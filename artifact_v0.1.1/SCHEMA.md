# v0.1.1 exact-input and receipt contract

This is non-load-bearing verifier hardening. The four certificate JSON files are
byte-for-byte copies of `../artifact_v0.1/`. No coefficient, root, physical state,
measurement phase or scientific theorem was changed.

## Strict boundary at each consumer

`strict_schema.py` is called by every current mathematical CLI, without a
separately remembered preflight. Duplicate JSON object keys, `NaN`, `Infinity`,
`-Infinity`, and overflowing nonfinite JSON numerals are rejected globally.
Finite floats and booleans remain legal **only in non-mathematical historical
annotations**, such as runtimes, numerical spectra and cached status flags.
They are rejected in exact scalars, rational endpoints, word factors, polynomial
coefficients, and structural block identifiers.

| Entry point | Required mathematical input files |
|---|---|
| `validate_integer_encoding.py` | All four JSON files |
| `verify_sos14.py` | `SOS14.json` only |
| `verify_statement.py` | `SOS14.json` only |
| `verify_independent.py` | `EXACT_KERNELS.json`, `EXACT_SOS_CANDIDATE.json`, `POSITIVITY_CERTIFICATE.json` |
| `kill_tests.py` | The same three Gram/positivity files |

Each consumed file receives full required-schema validation before arithmetic.
The compact route does not claim to authenticate unconsumed Gram bytes.
`validate_integer_encoding.py` establishes valid input syntax and required
structure, **not an SOS identity, positivity, or the theorem**. Internal
`verify_words` and `verify_positive` calls also validate their in-memory inputs.

### Exact scalar and rational types

A scalar has exactly `n` and `d`. `n` is a list of exactly 24 numerators and `d`
is strictly positive. A rational has exactly `numerator` and `denominator`,
with strictly positive denominator. Both forms accept JSON integers or strings
matching `0|-?[1-9][0-9]*`. In strings, leading zeros, `-0`, `+1`, whitespace,
decimals, exponents and empty strings are rejected. Boolean and floating-point
aliases are rejected too. A JSON numeric `-0` is the integer zero under the JSON
decoder; the stricter spelling rule applies to integer strings.
Unreduced positive-denominator rationals are allowed and normalized by the
arithmetic engine. Missing members are errors, including a scalar with just `n`
or just `d`; recursively encountered redundant scalar records are also checked.

The numerator index is `a+2*b+6*c+12*e`, for
`s^a*(5*mu)^b*u^c*i^e`, with `a,c,e in {0,1}`, `b in {0,1,2}`.
This convention is enforced independently of any input annotation.

### Word and Gram structures

A word is a JSON list of `[r,k]` pairs. **Actual JSON integers only** are accepted
for factors: no integer strings, booleans, or integral floats. `r` is in `0..3`
and `k` in `1..4`; even generators belong to Alice, odd to Bob. Canonical words
put Alice's factors before Bob's, preserve their order within each party, and
combine adjacent equal generators. Canonical compact words contain at most one
Alice and one Bob factor, hence are `1`, `A`, `B`, or `AB`.

`Q` is explicitly validated as 81 canonical compact words before the Gram
consumer compares it with the independently constructed ordered basis. E is
81 by block-size; H and L are square with the block-size, and D has that length.
The required five labels are `1,6,7,8,9` with sizes `2,4,3,3,2`. These labels are
identifiers, not a claim that nine blocks exist. Required keys and dimensions
are checked; optional historical fields do not substitute for them.

### Canonical policy versus mathematical truth

`SchemaError` means the supplied exact input is malformed or contradicts a
required declaration. `CanonicalFormatError` is a subclass marking a packaging
restriction; it must never be reported as a mathematical refutation.

- Explicit zero polynomial records are allowed. Compact output separately
  reports `stored_polynomial_records` and `nonzero_polynomial_coefficients`.
  The legacy `explicit_polynomial_coefficients` field means stored records.
- Duplicate diagnostic term IDs are rejected for traceability, even though
  labels do not affect the sum.
- Duplicate polynomial words and equivalent noncanonical word encodings are
  rejected as canonical collection policy, not because their sum is false.
- Summand permutations, nonzero common phases, and positive rescalings with
  compensating weights remain mathematically acceptable when the exact
  coefficients and the positivity proof still pass. Unreduced rationals are
  accepted. The checker does not require a fixed hash to authorize arithmetic.
- Compatible conjugate embeddings preserve the formal identity; they do not
  automatically preserve the positive branch or the physical conventions.
  This release certifies the fixed actual embedding in `ROOT_EMBEDDING.md`.

## Enforced target and historical annotations

The receipt's `enforced_target` is generated by the checker, never copied from
an unchecked theorem label. It records the theorem identifier, **descending**
polynomial coefficients `[5,0,-65,0,144,96,16]`, largest-root selector,
scalar basis, actual embedding, operator relations, and all eight standard
CGLMP events with `k=0,1` and weight `1-k/2`. Changing an enforced declaration
rejects input, even if some other scalar data would happen to pass.

`SOS14.json`'s theorem, root, relations, scalar_encoding and mu_polynomial are
required declarations and checked against that convention.
`EXACT_SOS_CANDIDATE.json`'s target and mu_polynomial are likewise checked.
`EXACT_KERNELS.json`'s Q and the E matrices, and the H/L/D, gamma and embedding
boxes actually consumed by a route, are mathematical inputs.

All other top-level fields are reported in each input's
`unverified_top_level_annotations`. Nested historical material is also
non-authoritative: kernels' `K`, exponents, rank, pivots and annihilation flags;
stored word universes; candidate reconstruction parameters, ranks and spectra;
positivity cached flags, pivot enclosures, physical_strategy summaries, decimal
displays and reported lower bounds. Their scalar/fraction/word syntax is checked
where applicable, but their claims are **not** accepted as proof premises.
Unknown added fields are annotations; their presence never changes the target.
The compact terms' IDs are enforced only for uniqueness, not mathematical
meaning. Unknown term-level fields are annotations too.

`EXACT_KERNELS.json:field_relations_file = exact_field.py` is a historical
reference to discovery code omitted from this reduced payload. It is not a
missing dependency. `EXACT_SOS_CANDIDATE.json`'s
`EXACT_IDENTITY_PASSED_POSITIVITY_NOT_YET_CERTIFIED` is historical discovery
status. Actual positivity is recomputed. These strings are preserved verbatim.
`PROOF.md`'s historical novelty-audit reference and its original generation
status likewise do not add prerequisites or claim current evidence.

## Receipt, exit and execution contract

Each successful current CLI includes `receipt` with:

- Version, entrypoint, exact enforced target and canonical target digest
- Actual consumed input bytes' SHA-256, length and resolved path
- Source snapshot hashes for the current verifier directory's Python files
- Available proof/schema/embedding/README document hashes
- Exact checks performed, interpreter/version/platform, optimization flags,
  command arguments, input root, working directory and UTC time

Document hashes identify prose bytes. `verify_statement.py` checks hard-coded
formulas corresponding to the proof; it does **not** parse arbitrary prose or
certify modified proof text. A missing or changed document therefore does not
silently become an enforced theorem: compare its hash with the release manifest
and inspect `document_hash_scope`. Hashes alone authenticate neither execution
history nor external validation. The receipt does not prove itself trustworthy.

Run with normal Python. `-O`, `-OO` and nonzero `PYTHONOPTIMIZE` are refused,
including an environment flag suppressed by Python's `-E`/`-I`. No exact
invariant is an optimization-removable assert. A caught schema/arithmetic
failure emits `status: FAIL`, overwrites the requested output with that failure,
and exits nonzero. Argument/import errors also exit nonzero and may produce no
receipt. A pre-existing output file after such an error is stale, not evidence.
Acceptance must check exit code **and** the intended status, exact residual and
fresh input/source binding. `UPPER_BOUND_ONLY_PASS` from `--skip-physical` is
not full-theorem `PASS`. Syntax-only `PASS` is not mathematical certification.

Historical receipts under `verification/` were copied unchanged for provenance;
they predate this contract and are never upgraded by the new checker version.
The current source manifest is relative to this directory. The root release
manifest and original-to-revised maps bind the package; preserve both original
failed/partial receipts and current runs separately.
